# 数据库表设计评审意见

> **评审依据**：《肿瘤科智能检测门诊系统 - 业务功能文档（学生开发版）》+ 《后端接口文档 V1.0 (47接口)》
>
> **评审日期**：2026-07-27
>
> **原始设计版本**：V2.0（8 张表）
>
> **评审结论**：整体设计覆盖面较完整，核心业务流程所需数据均可承载。以下按 **严重 / 中等 / 建议** 三个级别列出需关注的问题，其中严重项建议在开发前修复。

---

## 一、严重问题（建议开发前必须修复）

### 1.1 users 表 — 缺少 Laravel Auth 标准字段

**问题**：当前表缺少 `email_verified_at` 和 `remember_token` 字段。

- `email_verified_at`：Laravel 认证体系的标准字段，虽然当前注册接口未做邮箱验证，但预留该字段不会增加开发成本，后续若启用验证也无需改表。
- `remember_token`：登录接口（`POST /api/auth/login`）的请求体已包含 `remember` 参数（`"是否记住登录，默认 false"`），但表中无对应字段存储 Remember Token，Laravel Auth 的 `attempt()` 方法依赖此字段。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `email_verified_at` | TIMESTAMP, nullable | 邮箱验证时间 |
| `remember_token` | VARCHAR(100), nullable | 记住登录令牌 |

### 1.2 drugs 表 — 缺少库存预警阈值

**问题**：业务文档明确要求「库存不足时自动提示异常」，接口文档中也存在：

- 药品列表查询参数 `low_stock: boolean`（"仅显示库存不足药品"）
- 响应字段 `is_low_stock: boolean`（"是否库存不足"）
- 医生工作台仪表盘统计 `low_stock_drugs: number`（"库存不足药品数"）

但 `drugs` 表中没有任何字段来定义"库存不足"的标准，代码只能硬编码阈值（如 `stock_quantity < 10`），不同药品的预警标准应当不同（廉价辅助用药可多备，昂贵靶向药可少备）。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `low_stock_threshold` | INT (Unsigned), default 10 | 库存预警阈值，当 `stock_quantity <= low_stock_threshold` 时视为库存不足 |

### 1.3 prescription_items 表 — 缺少药品价格快照

**问题**：药品价格会随时间变动（调价、批次不同等），但 `prescription_items` 只记录了 `drug_id` 和 `quantity`，没有记录开具处方时的药品单价。业务文档要求患者"查看处方药品信息"后确认取药，如果无法获取价格，就无法展示费用明细。

虽然可以通过 JOIN `drugs` 表获取当前价格，但若处方开具后药品调价，历史处方显示的价格将与实际不符，存在数据一致性问题。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `unit_price` | DECIMAL(10,2) | 开具处方时的药品单价，从 `drugs.price` 快照 |

## 二、中等问题（影响功能完善性，建议优先修复）

### 2.1 users 表 — 缺少患者人口学信息字段

**问题**：当前仅有 `name` + `email` + `phone` 三个个人信息字段。对于肿瘤科医疗系统，以下字段有实际业务价值：

- **性别** (`gender`)：多种肿瘤的发病率与性别高度相关（如乳腺癌、前列腺癌）
- **出生日期/年龄** (`birth_date`)：肿瘤风险与年龄密切相关，AI 诊断时年龄是重要参考维度

接口文档中 PUT `/api/auth/profile` 仅开放 name 和 phone 的更新，也侧面说明当前缺少更多可编辑的个人信息字段。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `gender` | ENUM('male','female','other'), nullable | 性别 |
| `birth_date` | DATE, nullable | 出生日期 |

### 2.2 users 表 — 管理员无法设置医生的专业信息

**问题**：表中定义了 `title`、`specialty`、`department`、`introduction`、`experience_years` 五个医生特有字段，但：

- 管理员创建用户接口（`POST /api/admin/users`）的请求体只有 `name / email / password / role / phone`，**不含任何医生特有字段**
- 管理员编辑用户接口（`PUT /api/admin/users/{id}`）的请求体只有 `name / email / phone / role`，也**不含医生特有字段**
- 业务文档要求患者「查看所有肿瘤科医生信息」后选择医生预约，如果医生没有 title（职称）、specialty（专长）、introduction（简介），患者无法做出选择

**建议**：在管理员创建和编辑医生的接口中，增加医生特有字段的可选参数（当 `role=doctor` 时可用）。

### 2.3 appointments 表 — 缺少状态流转时间戳

**问题**：业务文档描述的就诊流程包含明确的时序节点：

> "医生登录系统，查看当日患者预约列表，**手动叫号**接诊患者"
>
> "医生接诊患者后，填写专属肿瘤科病历，可编辑、查看历史接诊病历记录"

接口文档也提供了对应的操作接口：

| 接口 | 状态变更 |
|------|----------|
| `POST /api/doctor/appointments/{id}/call` | pending → called |
| `POST /api/doctor/appointments/{id}/start` | called → in_progress |
| `POST /api/doctor/appointments/{id}/complete` | in_progress → completed |

但数据库表中只有 `created_at` 和 `updated_at`，无法追踪每个节点的具体时间。对医疗系统而言，记录每步操作时间（尤其是叫号时间、接诊开始/结束时间）是基本要求。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `called_at` | TIMESTAMP, nullable | 叫号时间 |
| `started_at` | TIMESTAMP, nullable | 开始接诊时间 |
| `completed_at` | TIMESTAMP, nullable | 结束接诊时间 |
| `cancelled_at` | TIMESTAMP, nullable | 取消时间 |
| `cancel_reason` | VARCHAR(255), nullable | 取消原因 |

### 2.4 prescriptions 表 — 缺少取药时间和备注

**问题**：

- **取药时间**：处方状态从 `pending → dispensed` 由患者确认取药触发（`POST /api/patient/prescriptions/{id}/dispense`），应记录操作时间，当前只能通过 `updated_at` 间接推测。
- **金额汇总**：虽然可以在应用层通过 JOIN + SUM 计算，但作为核心业务数据，在处方表冗余一个 `total_amount` 更便于查询和展示。
- **医嘱备注**：`prescription_items.instructions` 是每条药品的用药说明，但处方整体可能需要一段额外医嘱（如"两周后复诊"），当前无处存放。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `dispensed_at` | TIMESTAMP, nullable | 取药时间 |
| `total_amount` | DECIMAL(10,2), nullable | 处方总金额（可通过明细计算，但冗余便于查询） |
| `notes` | TEXT, nullable | 处方整体备注/医嘱 |

### 2.5 drugs 表 — 缺少药品状态字段

**问题**：药品可能因停产、更换供应商等原因需要停用。如果直接删除记录，历史处方中的 `drug_id` 外键将失效。当前设计没有软删除或状态标记，无法标识"停售"药品。

**建议**：

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `status` | ENUM('active','discontinued'), default 'active' | 药品状态；停售药品不应再被新处方引用 |

### 2.6 缺少 Laravel 生态的必要辅助表

**问题**：当前设计仅包含 8 张业务表，未包含框架运行所需的辅助表：

- `password_reset_tokens` — 密码重置功能（Laravel 内置）
- `personal_access_tokens` — Sanctum API Token 认证（接口文档明确使用 Laravel Sanctum）

这些表可以通过 Laravel 自带命令自动生成（`php artisan migrate`），但应在设计文档中明确提及，避免被误认为遗漏。

## 三、优化建议（不影响核心功能，建议后续迭代考虑）

### 3.1 ai_diagnoses 表 — 字段命名统一

**问题**：文字诊断的 `risk_level` 和图文诊断的 `risk_assessment` 语义相同（都是风险等级：低/中/高风险），但字段名不同。建议统一为 `risk_level`，减少理解成本。

### 3.2 ai_diagnoses 表 — confidence 字段类型

**问题**：`confidence` 使用 VARCHAR(10)，存的是 "92%" 这样的字符串。如果后续需要做统计分析（如"平均置信度"、"低于80%的报告"），字符串类型无法直接计算。建议改为 DECIMAL(5,2)（如 0.92），前端格式化时拼接百分号。

### 3.3 medical_records 表 — 缺少备注字段

**问题**：肿瘤科病历除了核心诊断信息外，医生可能需要补充额外说明（如建议进一步检查、复诊建议等），建议增加 `remark` 字段。

| 新增字段 | 类型 | 说明 |
|----------|------|------|
| `remark` | TEXT, nullable | 补充说明/复诊建议 |

### 3.4 索引优化建议

**高频查询场景对应索引检查**：

| 查询场景 | 建议索引 | 当前状态 |
|----------|----------|----------|
| 医生查看某日预约列表 | `(doctor_id, appointment_date, status)` | ⚠️ 仅有单独索引，无联合索引 |
| 患者查看自己的预约 | `(patient_id, status)` | ✅ 已有 |
| 患者查看某状态处方 | `(patient_id, status)` | ✅ 已有 |
| 按药品查库存变动 | `(drug_id, created_at)` | ⚠️ 仅有 drug_id 索引 |

**建议**：为 `appointments` 表增加 `(doctor_id, appointment_date)` 联合索引，这是医生端最高频的查询。

### 3.5 患者并发约束的数据库保障

**问题**：文档定义"患者同时只能有 1 个进行中预约"，当前完全依赖应用层校验（WHERE + COUNT + INSERT），在高并发场景下存在竞态条件。

**建议**：
- 方案 A（MySQL 8.0.13+）：使用 `UNIQUE INDEX` 配合 `IF( status IN ('pending','called','in_progress'), patient_id, NULL)` 函数索引
- 方案 B（通用）：在应用层使用数据库悲观锁（`SELECT ... FOR UPDATE`）或 Redis 分布式锁
- 方案 C（当前可接受）：应用层乐观锁校验 + 日志告警，对学生项目足够

### 3.6 医疗数据软删除机制

**问题**：当前所有表都没有 `deleted_at` 软删除字段。医疗数据通常不允许物理删除，建议对核心业务表（appointments、medical_records、prescriptions）增加软删除机制。

> ⚠️ 注意：用户规范规定「不允许主动修改数据库结构」。本建议仅供后续评审后授权修改时参考。

### 必须修复（阻塞开发）
